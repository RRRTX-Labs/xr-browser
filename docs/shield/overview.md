What is ours, what is the engine's, and the one interface between them.

## 1. Ours vs the engine

**Ours (xr-core/shield/, std-only C++20, zero I/O, zero Chromium
includes):** the decision core — request normalization, bundle grammar +
strict parsing, scope/exception resolution, apply sequencing, BlockEvent
ledger rows, and the fail-open/fail-closed posture decision. The core never
embeds an engine: `core/match.cc` talks to an *injected* `BlockingEngine`.

**The engine (adblock-rust 0.13.3, vendored at
`xr-core/third_party/rust/adblock/0.13.3/`):** list-driven filter matching
only, behind the same interface — either the deterministic std-only
`FakeEngine` (`core/fake_engine.{h,cc}`, mirrored byte-for-byte by the
Python fake `xr-core/fakes/shield.py`) or the Rust FFI shim
(`shield/engine/{lib.rs,xr_shield_engine.h,Cargo.toml}`, built on the
hosted/farm lanes only — never claimed built where cargo is absent, per the
runner-capabilities ledger law).

| core file | role |
|---|---|
| `core/context.{h,cc}` | request context normalization (lowercased surface, host anchoring) |
| `core/bundle.{h,cc}` | `xr-list-bundle` v1 strict grammar; attribution rides INSIDE the list digest |
| `core/match.{h,cc}` | the decision call — delegates filter matching to the injected engine |
| `core/scope.{h,cc}` | exception scopes + per-site toggles (exceptions are not waivers — ADR-0046) |
| `core/apply.{h,cc}` | bundle apply sequencing: monotonic version, LKG, hot-pin-out |
| `core/events.{h,cc}` | `block-event-v1` ledger rows (`MakeLedgerRow`), redaction at the source |
| `core/posture.{h,cc}` | the ONE fail-open/fail-closed decision site |
| `core/engine.h` | the injected `BlockingEngine` interface + `Action` vocabulary |
| `core/fake_engine.{h,cc}` | the deterministic table engine (law comments pin the v1 semantics) |

## 2. The interface (`core/engine.h`)

`Action` is a closed vocabulary: `block | allow | redirect | replace`
(`kAllow` = an exception rule `@@` matched — observed-but-allowed). The
mojom `BlockAction::kUpgraded` (HTTP→HTTPS) is a network-layer action no
list rule produces in v1 — deliberately absent from the engine vocabulary
and documented as such at the enum. `EngineHit` carries `action`,
`rule_id`, `list_id` — the provenance P13's "why was this blocked?"
explainers consume (100% of events carry rule-id + list, plan §4 row).

Engine DEATH is representable and total: `alive()` flips false, `Match`
stops being called, and `posture.cc` turns that into fail-OPEN browsing
with an amber chip — never a crash, never a silent allow-with-green.

## 3. Both bindings, one protocol

* **C++ host** — `xr-core/shield/host/shield_host.cc`: the stdio host
  process. TWO vocabularies (registry row `shield-host-protocol v1` in
  `docs/contracts/registry-post-freeze.md`): the FROZEN mojom envelope for
  `Status`/`RecentEvents`, and the LIVING host method surface
  (`flag-status`, `bundle-load`, `bundle-check`, `match`, `posture`,
  `apply`, the T4 exception surface `exception-add/remove/sweep`,
  `site-toggle`, the T5 emitter `event-emit`, the T6 dev-only page methods
  `page-states`/`debug-page`). Method table + usage string:
  `xr-core/shield/host_protocol.md` (the T0-a doc; `tools/host_protocol_check.py`
  keeps host/registry/doc in lockstep).
* **Python fake** — `xr-core/fakes/shield.py`: byte-parity mirror of the
  host. Golden vectors pin BOTH backends: 307 cases in
  `docs/contracts/vectors/shield-v1.json` (≥150 floor) regenerated by
  `tools/gen_shield_vectors.py` + the T4/T5/T6 family extensions
  (`tools/shield_vector_families*.py`), replayed byte-identical through both
  backends in `run_checks.sh`.

## 4. Posture — the asymmetry, encoded once

`DecidePosture` (inputs: `route_loss`, `engine_dead`, `engine_poisoned`,
`kill_switch_on`) fixes precedence **route > engine > kill-switch > normal**:

* route loss ⇒ fail-**CLOSED**, absolutely (a lost network route must not
  browse unfiltered);
* engine death/poison ⇒ fail-**OPEN** with an amber chip ("off is a visible
  state, never a green lie");
* kill switch (`xr_shield_v1` off / enterprise force-disable) ⇒ fail-OPEN,
  amber, `kill-switch` reason;
* a kill switch cannot un-fail-close a lost route (precedence).

Property-tested by exhaustive 16-combination enumeration in
`xr-core/shield/tests/test_posture.cc`; the inversion fixture is registered
in `tools/run_negatives.sh` (flipping the asymmetry reddens the suite).
Decision-site docs: the law comment in `core/posture.h` + this file.

## 5. Flag + laws

`xr_shield_v1` (default `on`) is the kill-switch for the whole surface;
both states are tested (golden vectors + `test_shield_host`); expiry /
retirement note: `docs/contracts/registry-post-freeze.md` §`xr_shield_v1`.
`shield/core/**` performs no I/O beyond the injected engine and no network
egress (enforced: the core-hygiene gate row in `tools/run_checks.sh` —
std/libc includes only, no Chromium, no cross-core escapes). S0 trust
classification: `docs/process/s0-paths.yaml` (`/shield/`, `/update/`).
