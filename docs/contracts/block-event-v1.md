## What it is

The Activity Ledger's row contract (the ledger UI itself is P13): every
network decision the shield makes — block, allow, redirect, exception,
degraded-posture fail-open/fail-closed — is recorded as one canonical row
that answers **"why was this blocked?"** with rule id, filter text, list,
bundle version, site-class origin, and a closed reason code. A row is an
EVENT, not a policy change: rows never move bundle pins, never alter
exception scopes, and never widen the frozen `policy-change-event-v1`
(brief §architecture invariant 7).

## Shape

```json
{
  "event": "block_event",
  "contract_version": 1,
  "seq": 41,
  "ts_millis": 1750000000123,
  "identity": "xr:00000000-0000-4000-8000-000000000001",
  "tab_id": 7,
  "origin": {"scheme": "https", "registrable_domain": "tracker.example"},
  "target": "https://tracker.example/ad.js",
  "rule_id": "r-1",
  "rule": "||tracker.example^",
  "list_id": "l-1",
  "bundle_version": 3,
  "action": "kBlocked",
  "request_class": "kScript",
  "why_code": "rule-blocked"
}
```

(The golden file is this row in canonical form: sorted keys, no
whitespace. Its `context.url` carried `?utm_source=newsletter#player` —
the row's `target` does not: see the redaction law.)

## Laws

- **Event, not policy.** The emitter writes the activity-ledger path
  (per-tab ring → ledger) and touches no policy state. It has no
  `kRejected` class: there is no content-conflict semantics in emitting
  an event, so every bad input is `kMalformedInput` (exit 1) with a
  closed-vocabulary detail token (`missing-seq`, `bad-action:<name>`,
  `bad-why-code:<code>`, …).
- **Superset, never a widening.** The row is a living document AROUND the
  FROZEN `BlockEvent` mojom vocabulary: `action` reuses the frozen
  k-spellings, `identity`/`tab_id`/`origin`/`target`/`rule`/
  `request_class`/`ts_millis` reuse frozen field semantics (numeric
  fields int64 on the wire, as the mojom declares — the T2-era int32
  casts in `EventToJson` truncated epoch-scale timestamps and were fixed
  alongside the emitter; frozen-surface bytes are unchanged for every
  value the frozen tests and vectors use). The mojom itself is
  untouched, and `policy-change-event-v1` stays exactly as frozen.
- **Redaction at creation.** `target` is `scheme://host/path` BEFORE the
  row exists — query strings and fragments are structurally absent
  (never a display-time concern). `rule` keeps the filter text: that is
  list content, not browsing data, and it is the user-facing "why"
  provenance.
- **Deterministic.** Same context + params ⇒ byte-identical row. `seq`
  (the caller's monotonic per-identity counter) and `ts_millis` are
  caller-supplied; the generator reads no clock (the
  `commands/core/dispatch.cc` ledger-row precedent).
- **Every decision is an event.** `why_code` draws from the closed
  verdict vocabulary (11 codes, `xr-core/shield/host_protocol.md`
  §Decision vocabularies); a row may record ANY verdict, not only
  blocks — the ledger accounts for allows and degraded-posture outcomes
  too (plan §data: every block/deny/grant decision carries its reason
  code).
- **Reason codes are a P13 render dependency.** `docs/shield/reason-codes.{md,json}`
  maps every `why_code` to a stable text key for the localized "why was
  this blocked" copy P13 renders. Codes never change; keys never change;
  the copy behind a key may. Until P13 lands, the code itself is the
  user-visible fallback string.
- **Retention and locality (browser-side, P13).** The ledger persists
  per-identity, locally only (SQLite in the plan's data section), with a
  90-day rolling default retention, user-configurable, exportable by
  user action, and **never uploaded**. v1 pins the row SHAPE and the
  redaction; persistence-time retention enforcement is P13's job and is
  documented here as a dependency, not claimed as implemented.
- **Ring and view caps carry over.** The per-tab ring's FIFO cap of 256
  events and the RecentEvents 64 KiB canonical-byte view budget
  (`kCapacity` / `kChunkBudgetBytes`, `xr-core/shield/core/events.h`)
  are the v1 host-scale of the plan's per-tab ring; the doc/code match
  is pytest-tested. The plan's 2,000-event browser ring is P13's scale
  of the same law.
- **Attention posture.** Rows feed the passive chip counter (invariant 7:
  the chip count is the ONLY passive counter) and ledger/dev-page
  listings — no toast, badge, or modal ever comes from the emitter.
- **Vocabulary sync (five-way law).** The `why_code` set is ONE closed
  vocabulary in five places at once: `host_protocol.md`, this schema's
  enum, `reason-codes.{md,json}`, the emitter's accepted set (both
  backends), and the vectors' usage — `test_block_event.py` asserts they
  agree; drift reddens.

## Consumers

- P13 Activity Ledger + Observatory (renders rows, export, retention
  enforcement, "why was this blocked" one-click via the reason-code
  table)
- `xr://shield` dev-only page (P11-T6; recent rows listing)
- The shield chip counter (passive counts only)
