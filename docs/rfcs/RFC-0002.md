## Summary

`PermissionPolicy` has exactly four `PermissionState` fields: geolocation, camera,
microphone and notifications. Plan T1 (line 803) lists more capabilities for the
per-identity overlay: clipboard-read-write, sensors, midi and pics. P15 kept the frozen
surface intact by making those four **deny-only data** (ADR-0051, envelope (ii)): the
overlay can record `kDeny` or `kAsk` for them, never `kAllow`, and they have no output
slot in the resolver's answer. This RFC proposes adding four `[MinVersion=1]` fields to
`PermissionPolicy` so the resolver can return a decided state for each extra. It is a
proposal only. Nothing in this phase edits `mojom/`.

## Motivation

ADR-0051's envelope (ii) is safe because it can only narrow: an extra recorded as
`kDeny` narrows upstream's answer, and a record that claims `kAllow` is corrupt. That is
enough for P15. It is not enough for the two phases that consume P15:

- **P35, the Fortress default-deny list** (plan line 815). Fortress identities must be
  prompt-less blocked for every prompt-capable capability. Today the resolver can only
  say "deny" for the frozen four. For the extras, the deny lives in the overlay and is
  applied by the host, outside the resolver's answer. A second place that decides is
  the "second brain" plan T1 forbids, and P35 cannot prove "zero prompts" from the
  resolver's output alone.
- **P21, Guard prompt ceilings** (plan line 815). Guard reads the resolver's decided
  state to know whether a prompt may be shown at all, before applying the attention
  ceiling. With no slot for the extras, Guard has nothing to read for them and must
  either guess (forbidden) or call the overlay directly (a second write/read path that
  `tools/permission_write_path_check.py` exists to prevent).

Without the widening, both phases either duplicate the overlay's logic or leave the
extras outside the resolver. Both are worse than a reviewed contract change.

## Proposed change

```
struct PermissionPolicy {
  PermissionState geolocation;
  PermissionState camera;
  PermissionState microphone;
  PermissionState notifications;
  [MinVersion=1] PermissionState clipboard_read_write;
  [MinVersion=1] PermissionState sensors;
  [MinVersion=1] PermissionState midi;
  [MinVersion=1] PermissionState pics;
};
```

- The default for each new field is `kDeny` (the first enum value, the safe default).
- The resolver fills the new fields with the same layer order ADR-0051 decision 1 uses:
  corrupt overlay, Fortress deny-list, per-identity default, temporary grant.
- Whether the overlay may then *widen* an extra to `kAllow` is a separate question.
  This RFC proposes **no**: the extras stay deny-only (`kDeny` | `kAsk`) in the overlay
  even after the widening, so envelope (ii) still holds and only the slot is new.
- Vectors: a new additive vector file for the extras; the 66 frozen vectors keep their
  expected values byte-for-byte (an old consumer sees the four original fields only).

## Alternatives

1. **Keep envelope (ii) as the final answer (do nothing).** No frozen change. P35 and
   P21 then read the overlay directly, which is the second decision point ADR-0051
   rejected (alternative R3).
2. **A separate `ExtrasPolicy` struct returned next to `PermissionPolicy`.** Avoids
   touching the frozen struct, but it is still a mojom change (a new field on the
   resolver's result), so it costs the same amendment and adds a second struct that
   every consumer must merge.
3. **Encode the extras in the existing `notifications` slot or in a string map.**
   Rejected outright: overloading a typed slot or adding an untyped map defeats the
   frozen enum and the deny-default law.
4. **Widen and allow `kAllow` for extras in the overlay.** Rejected for now. It changes
   envelope (ii) from deny-only to widenable and needs its own security review.

## Migration

Forward-only. `[MinVersion=1]` fields are absent for version-0 peers, which read the
four original fields only. `fakes/policy_resolver.py`, the vector file, the parity
corpus and the overlay projection gain the four slots in one change, behind the
`Contract-Amendment: RFC-0002` trailer, and only after a human has approved this file.

## Backward compatibility

Existing consumers see no change. The 66 frozen vectors keep their expected values. A
version-0 peer that receives a version-1 struct ignores the new fields (mojom
versioning).

## Security review

- The surface widens by four typed enum fields with a deny default. No generic exec,
  no new IPC method, no new dependency, no crypto, no egress.
- Deny-only stays the overlay law for extras (Proposed change, last bullet), so the
  widening cannot by itself produce an allow that upstream did not give.
- Not proven by this draft: the Chromium-side mapping of each extra to an upstream
  `ContentSettingsType` at the pin; that is part of the human review (`HG-P15-RFC2`).
